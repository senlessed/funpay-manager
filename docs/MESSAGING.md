# История и очередь — 0.1.0.dev1

История обновляется по запросу, не в фоне. chat/history возвращает ограниченное
число доступных сообщений; прежняя локальная история сохраняется. Дедупликация:
UNIQUE(local_chat_id, remote_message_id). Направление определяется author_id,
системный автор — 0. Текст покупателя не выполняется как команда, Telegram выводит
plain text. Изображения обозначаются типом, загрузки медиа нет.

В таблице chats уникальны (account_id, remote_id), nickname не ключ. Callback несёт
локальный ID и случайный route_key. Это защищает от устаревших кнопок после restore,
когда числовой ID мог быть повторно использован для другого покупателя.
Проверка владельца и private chat выполняется до MessageService.

Ответ привязан к сохранённому Telegram prompt ID, bot ID, private chat ID и chat FK,
TTL 15 минут. До подтверждения обработки update текст фиксируется в outgoing_messages.
Уникальны (bot_id,source_update_id) и (bot_id,telegram_chat_id,telegram_message_id).
Повтор update может повторить UI-ответ бота, но не создаст вторую операцию FunPay.

Очередь claim выполняет BEGIN IMMEDIATE. Один чат сохраняет FIFO: queued/sending/
unknown более ранней операции блокируют следующую; остальные чаты независимы.
Отправка opt-in, выключена по умолчанию. Worker не опрашивает SQLite постоянно
в простое, просыпается от события при добавлении/изменении разрешения. Перед claim
проверяется аккаунт сессии. Authentication error сохраняет queued с backoff.

Запись выполняет отдельный FunPayMessagingAdapter: перед POST получает доступную
историю, после POST требует подтверждения ответа и ровно один новый remote ID
с правильными chat/account/author/text. Старое совпадение текста не считается успехом.
HTTP/таймаут/неоднозначный ответ после границы записи → unknown; автоматического
повтора POST нет. Явный отказ сервера/ошибка до POST → failed. Подтверждение sent и
добавление исходящего в историю — одна SQLite транзакция; последующее echo не дублируется.
Cancelled sending и sending после аварии → unknown. Текст операции остаётся в SQLite.

Неопределённый результат нельзя безопасно сверить одним совпадением текста:
пользователь проверяет FunPay и закрывает операцию без повтора. Кнопки привязаны
к UUID операции, а не переиспользуемому номеру. Очередь имеет пагинацию. Закрытая
владельцем операция так и обозначена; она не выдаётся за подтверждённо недоставленную.
Автоматической повторной отправки failed тоже нет; новый ответ — новое действие владельца.

Restore сначала делает staged copy с выключенной отправкой, переводит queued/sending
в unknown и удаляет prompt contexts, затем SQLite backup API заменяет рабочую базу.
Без этого старый queued из бэкапа мог уже быть отправлен после даты создания копии.
Обычный restart отличается: queued остаются queued и могут продолжиться.

Контракт сверялся с [исходниками Account](https://github.com/LIMBODS/FunPayAPI/blob/master/FunPayAPI/account.py):
GET chat/history, POST runner с action=chat_message и объектом chat_node.
Новый код не использует старые HTTP-зависимости FunPayAPI. Живые аккаунты/ключи
не применялись: реальная совместимость сайта и доставки остаётся непроверенной.
Это ещё не полный SyncWorker, Topics, уведомления или публичный релиз.
