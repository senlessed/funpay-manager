# Синхронизация и уведомления — 0.1.0.dev2

FunPaySyncWorker и NotificationService — самостоятельные задачи backend loop.
Они не используют общую fail-fast TaskGroup. Текстовый sender и polling также
независимы. При restore/смене ключа службы останавливаются, сессии закрываются;
запуск и остановка защищены lifecycle lock. Ключи остаются в Credential Manager.

## Ограниченное чтение

Один цикл: authenticate → get_chats → до 5 get_history. Список ограничен 50 чатами,
история — доступным последним фрагментом FunPay. Две позиции выбираются по старейшей
проверке, остальные — по изменённому превью/непрочитанности и возрасту проверки.
Идентичный текст не служит ключом дедупликации. Ошибка одного чата не прекращает
остальные; ошибка auth/CAPTCHA останавливает автоматическое чтение и запись до
ручного возобновления. Остальные ошибки дают backoff до 300 секунд + jitter.
Статус «частично» не обновляет время полностью успешного цикла.

RequestGate сериализует HTTP-запросы всех экземпляров FunPay-адаптеров и выдерживает
не менее 2 секунд между началами запросов. Это консервативный локальный предел,
не утверждение об официально разрешённой частоте FunPay. GUI от сети не блокируется.

## Начальная точка и курсоры

SQLite schema 3 добавляет chat_sync_state и notifications. При первом снимке
списка все найденные чаты получают baseline_pending. Первый успешный get_history
такого чата сохраняет историю и watermark без уведомления. Начальные 50 чатов
могут обрабатываться несколько циклов; сообщения до первого чтения каждого
попадают в тихую начальную точку. Это сознательная граница покрытия.

После начальной регистрации списка новый обнаруженный чат уведомляет только
о последнем сообщении, если оно входящее. Формулировка «в обнаруженном чате»
не выдаёт старую впервые увиденную переписку за новое событие по времени.

Позднее уведомляются только remote ID > watermark от другого пользователя.
Системный автор 0, неизвестный -1 и собственный account ID не порождают входящих
уведомлений. Текст и курсор + notification outbox фиксируются в одной транзакции.
Даже если ручной просмотр уже сохранил сообщение, cursor обеспечивает его
уведомление один раз. UNIQUE(event_key,bot_id,owner_id) защищает от конкуренции.
Возобновление после выключенного ПК ограничено доступной историей: пропуск
более доступного окна восстановить целиком невозможно, полнота не обещается.

## Доставка Telegram

Используется тот же bot ID, отдельный клиент только для getMe/sendMessage, без
второго getUpdates. Перед claim проверяются действующие account/bot/owner и флаг
уведомлений. Цель — private owner ID; HTML parsing и URL preview отключены.
Уведомление содержит ограниченное превью и кнопку истории с route_key.
Размер учитывает UTF-16, поэтому эмодзи не ломают границу текста.

queued → sending → sent/failed/unknown. Перед сетью claim фиксируется в SQLite.
Таймаут/отмена/сбой после send boundary и sending после аварии → unknown без повтора.
403/невалидный запрос → failed. Это не exactly-once: Telegram мог принять сообщение,
даже когда локального подтверждения нет. unknown отображается в разделе уведомлений.
Автоматического повторного sendMessage для uncertain delivery нет.

retry_after даёт безопасный возврат в queued с persistent cooldown bot/owner.
Ожидание действует и на новые события, переживает restart и не сбрасывается
выключением уведомлений. Ошибка до claim оставляет queued и применяет backoff.
При пустой очереди или отключении worker ждёт события без постоянного SQL polling.
Сообщения отправляются не чаще одного за 1.1 секунды внутри worker; отдельные
интерактивные ответы бота могут также вызвать лимит Telegram, который обрабатывается.

Результат отправки покупателю (sent/failed/unknown) создаёт отдельное событие
в той же транзакции с изменением outgoing_messages. Это уведомление владельцу,
а не повтор текста покупателю. Сбой Telegram не изменяет исходящую операцию FunPay.

## Настройки и восстановление

Синхронизация и уведомления по умолчанию включены после подключения аккаунтов;
запись покупателям остаётся opt-in/off. Выключение синхронизации не выключает
ручную историю и queue sender. Выключение уведомлений закрывает queued события,
новые в это время не создаются, watermark продолжает двигаться. Уже начатая
отправка может завершиться. Пользовательская настройка уведомлений не возобновляет
sync, приостановленный из-за auth, неявно.

Restore поддерживает schema 1–4, отключает отправку, sync, уведомления и Topics,
переводит ожидающие доставки снимка в unknown, сбрасывает sync checkpoints.
После ручного возобновления делается новый тихий baseline, без всплеска старых
уведомлений. База перед заменой проходит staged preparation и safety backup.

Контракты и ограничения сверены с [Telegram FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this)
и [исключениями aiogram](https://docs.aiogram.dev/en/latest/dispatcher/errors.html).
Проверки используют временную SQLite, mock Bot/адаптеры, в том числе 100 событий
с повторными ingest и перезапуском. Это не live integration и не длительный soak.
